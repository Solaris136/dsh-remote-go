# DSH 远程入口 · 薄客户端设计（Remote-SSH 式）

> 版本 v0.6 · 2026-11-10 · 状态：内容设计稿（产品决策已确认；补充同类项目调研与远端运行时/运维管理）
> 项目：`dsh-remote-go`（中文名「DSH 远程入口」）· 仓库：https://github.com/Solaris136/dsh-remote-go
> 范围：**只定义插件提供什么内容、长什么样、怎么用**；不含架构、接口、代码、部署。
> 替代关系：本版取代 v0.2「全控制台」方案（历史稿不随仓库保留）。
> 关联调研：同类项目与需求/注意点的汇总结论见 §15（早期调研报告已不再随仓库保留，可从 git 历史取回）。

## 0. 摘要

**方向**：按 VS Code Remote-SSH 的思路做——**运行时整体留在服务器，本地只做「连接 + 窗口 + 状态」三件事**。

- 本地插件内容只有 6 块：**主机清单、接入向导、整窗接管（呈现远端 DSH 界面）、连接状态与诊断、设置、可选的通知提醒**。
- 会话、审批、文件、终端、插件、凭据、日志——**全部在远端 DSH 自己的界面里完成**，本地不重做一套。
- 本地代码量以「天」计（V1 约 1–2 周含打磨），而不是 v0.2 全控制台方案的 7–9 周。

**一条关键结论（决定方案选型）**：DSH 目前**没有**「本地原生界面直连远端 Host」的产品化能力（`dsh-api-remotes` / `dsh-experimental-liveshare` 等现有 Remote 能力方向是反的：把本机 Host 分享给别的客户端）。所以「VS Code 那种同一套原生 UI 渲染远端数据」在 DSH 里没有现成开关；要做成那样，本地必须加一层桥接（会话映射 / 事件回灌 / 审批桥），本地工作量反而不小——那就是 v0.2 和 `dsh-remote-local-plugin` 走的路线。

**DSH 桌面端提供 Chromium guest 通道**：插件可以请求一个独立 browser guest，把远端 DSH 自己的完整 Web 界面渲染在**整个窗口（本地侧边栏让位）**。因此最贴合「本地只渲染」的做法是：**远端界面交给 guest 承载，本地只负责 SSH 连接、整窗接管与状态**；DSH 面板只承载本地页面（主机管理），不再承载远端界面。本版按这个方向设计，能力依据见 §4.3 / §7.0。

**v0.6 增补**：远端只要 Linux + 能访问 nodejs.org/npmmirror 与 npm registry 即可——插件把**自己的 Node** 固定安装到 `~/.dsh/remote-go/node`（版本取本机 DSH `engines.node` 的下限、官方 tarball + SHA-256 校验、不需要 root、永远不动系统 Node），再用 `npx` 精确版本拉起 DSH；远端版本与**本机一致**；本机关闭后远端可**继续存活**（按主机可配）；远端的**插件管理走远端 DSH 插件市场**（在远端界面内，本地不单独实现），**设置**可在本机配置（Diff/备份/重启提示）。详见 §16。

**分期**：V1.0 整窗接管 + 主机管理 + 诊断 + npx 运行时/版本一致/存活策略 → V1.1 沉浸模式 + 多主机 + 通知桥 → V1.2 设置管理/打磨 → V2 评估「原生渲染」增强。

## 1. 设计原则与 VS Code 对照

| 职责 | VS Code Remote-SSH | 本设计（DSH 远程入口） |
|---|---|---|
| UI 呈现 | 本地 VS Code 界面 | 桌面端 Chromium guest 在**整窗**承载**远端 DSH 自己的界面**（本地侧边栏让位，内容区底部注入 远端侧边栏注入的主机条） |
| 运行时（agent/工具/模型/会话） | 远端 VS Code Server | 远端 DSH |
| 文件 / 终端 / 扩展 | 远端 | 远端（远端 DSH 界面自带） |
| 传输 | SSH | SSH |
| 本地保存什么 | 连接信息、最近打开、设置 | 主机清单、连接状态、窗口与显示设置 |
| 本地不做什么 | 不跑扩展宿主、不读远端文件 | 不实现会话/审批/文件/终端/DSH 管理界面 |

**三条原则**：

1. **能在远端做的，一律在远端做**：本地不复制远端已有能力。
2. **本地只保留三类内容**：连接（SSH/隧道）、呈现（整窗接管/未来的沉浸层）、状态（主机与连接状态）。
3. **远端 DSH 保持原版**：不要求服务器安装任何本插件专属组件；远端界面是什么样，本地就看到什么样。

## 2. 职责边界

| 本地插件 | 远端 DSH |
|---|---|
| 保存主机清单与连接配置 | 运行 agent 循环、工具、模型调用 |
| 建立/保持/重建 SSH 连接与隧道 | 持久化会话与事件 |
| 在整窗接管并呈现远端 DSH 界面 | 渲染会话、审批、文件、终端、插件管理、设置、凭据、日志 |
| 显示连接状态、加载状态、错误与诊断 | 处理审批与提问、执行命令、读写文件 |
| 记住连接参数、语言、安全选项 | 版本升级、插件安装、凭据轮换（在远端界面里操作） |
| 可选：把远端提醒转成本机通知 | 提供"当前需要人处理"的状态 |

**明确不做（本地）**：不重写会话视图、不实现审批面板、不做文件浏览器/编辑器、不做终端、不做 DSH 管理页、不做多机任务编排界面。

## 4. 本地页面内容设计

### 4.1 主机清单（侧边栏「远程入口」入口）

**目标**：一屏看到所有服务器，点一下就进去。

**内容**：

- 顶部：标题「远程入口」+「添加主机」主按钮 + 刷新状态。
- 主机卡片：显示名、SSH 地址（用户名@主机:端口，可脱敏）、状态（未配置/连接中/已连接/断开/错误/受限）、远端 DSH 版本、上次打开时间。
- 卡片操作：打开（接管整窗）、连接/断开、编辑、删除；错误时显示「诊断」。
- 汇总条：已连接 N / 总共 M；可选显示「有提醒的主机」。
- 最近打开区（P1）：最近 3 台，一键回到上次的视窗。

**空态**：「还没有服务器。添加一台，然后在本地窗口里直接使用它上面的 DSH。」+「添加第一台服务器」。

**异常态**：卡片顶部红色细条 + 一句原因（分类见 §8.4）+「诊断」。

### 4.2 接入向导（3 步）

**步骤 1 · SSH 信息**

- 显示名（默认取地址/别名）、SSH 地址或本机 SSH 配置别名、端口、用户名。
- 认证：使用**私钥文件**（默认 `~/.ssh/id_ed25519`，可浏览选择）或**密码**（可记住，存 DSH 凭据存储）；不支持 SSH Agent。
- 跳板机（可选）：选另一台已添加主机或填写地址。
- 提示：密码默认不保存（勾选后才写 DSH 凭据存储）；密钥只读路径、不上传。

**步骤 2 · 连接测试**

- 进度：网络可达 → SSH 认证 → 主机指纹确认 → 读取系统信息。
- 首次连接展示主机指纹，要求确认；指纹变化时强提示。
- 失败按类提示：网络 / 认证 / 指纹 / 系统不支持，并给下一步。

**步骤 3 · 远端 DSH 探测与完成**

- 探测结果用「能力清单」展示，不让用户理解技术细节：
  - 系统：Linux x64 / Ubuntu 24.04（信息展示）。
  - 远端运行时：托管 Node 是否能安装/升级（Linux 架构、glibc、磁盘、能访问 nodejs.org 或 npmmirror）、`npx` 能否解析到与本机相同的 DSH 版本（不满足时给出可执行的原因与下一步）。
  - 远端界面：可启动 / 已在运行（可直接复用）/ 无法启动（显示原因）。
  - 模型凭据：已配置 / 缺失（提示在远端界面里配置）。
  - 远端宿主设置：检查是否会被误判为「本机工作站」（目录对话框 / Open In / 自动开浏览器），给出修正提示（详见 §15.2 P5）。
- 启动方式（若未运行）：由插件在远端启动界面服务（推荐）/ 用户提供已有地址与访问令牌 / 稍后手动处理。
- 完成：摘要 +「打开远程入口」；失败可重试、可复制诊断、可保存为「未就绪」主机。

### 4.3 远程入口（核心页面）

**目标**：在本地 DSH 里使用远端 DSH 的完整界面，窗口里只出现一个侧边栏。

**呈现形态只有一种：整窗接管。** 远端 DSH 由桌面端自带的 browser-guest 通道以真正的 Chromium guest 渲染：
`window.dshDesktop.browser.acquire(workspace)` 拿到 lease 与 partition，页面创建
`<webview src="about:blank#<lease>" partition=...>` 挂到 `document.body`，`dom-ready` 后 `loadURL(隧道 URL)`。
guest 是独立浏览器上下文（自己的 cookie），不是 iframe；它铺满**标题栏以下的整个窗口**。本地侧边栏在接管期间被盖住，
因此窗口里唯一的侧边栏是远端自己的那个——不会出现「本地侧栏 + 远端侧栏」并排的两条栏。

- 放行规则（壳）：guest 只允许 http(s)、无账号密码、且不是「当前应用 host」；判定是
  `url.port === hostUrl.port && (同 hostname || loopback)`，隧道端口与本地 DSH 端口不同，因此放行。
- 代价（壳写死）：guest 会话 `will-download` 被 preventDefault（下载不可用）、所有权限请求拒绝、弹窗转交宿主；应用重载后浮层需重建。
- 载体挂在 React 树之外，切换面板不会销毁；切换主机或卸载面板时释放 lease 并移除。
- 浏览器里无 `window.dshDesktop`：没有可用的远端呈现方式（也没有内嵌或独立窗口的退路）。

**注入的主机条。** 接管期间不做本地覆盖，而是把一条**主机条注入远端页面自己的侧边栏**（品牌行下面）：状态点 + 主机全名（点开切换）+ 远端会话名，菜单里带刷新与「离开远端」。它用远端页面的 CSS 变量绘制，随远端主题、hover 与弹层遮罩一起变化。不再有本地兜底条——注入失败就是失败，宁可没有控件也不要一条看起来像外挂的横条：

- 每台已配置主机一个按钮：名称缩写（ASCII 取前两个字符，中文取首字）+ 状态点 + 悬停显示完整主机名。
- 点另一台主机即切换（未连接的主机先回到主机管理页显示连接进度，连上后自动重新接管）。
- 底部两个动作：**刷新**（重载 guest）与**离开远端**（回到主机管理页；SSH、隧道与远端任务都不停）。
- 一条主框架失败提示：远端界面加载失败时在 guest 区域显示一行普通文字（"远端界面加载失败，请刷新后重试，或从底部主机条回到主机管理"）。

**进 / 出 / 换，三个动作。**
- 进远端：侧边栏「远程主机」→ 主机管理页 → 目标主机「打开」。
- 换远端：接管期间在主机条的主机下拉里选另一台。
- 回本地：点主机条右侧的「离开远端」回到主机管理页，再点侧边栏的本地工作区 / 会话（面板卸载即 `closeOverlay()`，这是生命周期规则，不是全局点击监听）。

**面板内容**：主机管理页本身（清单 / 添加 / 编辑 / 诊断 / 删除 / 打开 / 断开）。面板内没有工作区栏，
也没有接管状态面；主机管理从不承载远端界面，远端界面也从不嵌进管理页。

**关闭行为**：离开远端 = 关闭本地承载，不结束远端任务；首次离开时提示一次「远端任务会继续运行」。

### 4.4 连接状态与诊断

**入口**：主机卡片「诊断」、设置页。

**内容**：一张检查表——SSH 可达性、认证方式、主机指纹、隧道状态、远端服务是否运行、远端界面是否可打开、远端 DSH 版本、模型凭据状态。

- 每项：通过/失败/未知 + 一句话说明。
- 操作：重新检查、复制诊断信息、查看最近连接日志（连接层，不含远端会话内容）。

### 4.5 设置

**窗口**：关闭视窗行为（固定为"保留远端会话"）。呈现方式没有可选项：接管整窗是唯一形态。

**SSH 默认值**：默认端口、默认认证方式（私钥文件 / 密码）、默认密钥文件路径（`~/.ssh/id_ed25519`）、默认跳板机、连接超时、自动重连开关与次数。

**安全**：主机指纹策略（首次询问/严格校验）、是否允许保存访问令牌（默认不保存）。SSH 密码可选保存进 DSH 凭据存储（仅当前用户可读的明文 YAML，非加密库，界面与文档均如实标注）。

**通知（P1）**：是否启用远端提醒、免打扰时段、是否显示远端任务完成提醒。

**其他**：语言、日志级别。

### 4.6 通知提醒（可选，P1）

- 触发：远端出现待审批 / 任务完成 / 远端会话报错（需用户在设置中开启）。
- 形式：本机通知 + 主机卡片标记；点击回到对应远端视窗（尽可能定位到对应页面）。
- 限制说明：这是本插件唯一需要"本地感知远端状态"的能力；V1 可先不做，保证"纯渲染"的简单性。

## 5. 核心流程

### 5.1 首次连接（目标 ≤ 3 分钟）

| 步骤 | 用户看到 | 用户做 |
|---|---|---|
| 1 | 主机清单空态 | 点「添加第一台服务器」 |
| 2 | SSH 表单 | 填地址/认证方式 |
| 3 | 连接进度 | 确认指纹 |
| 4 | 远端环境探测结果 | 确认启动（npx 固定本机版本） |
| 5 | 远端 DSH 界面接管整窗 | 开始使用（后续操作都在远端界面里） |

### 5.2 日常打开

打开本机 DSH → 侧边栏「远程主机」→ 点主机「打开」→ 自动连接 → 整窗接管为远端界面。已连接过的机器目标 ≤ 10 秒。

### 5.3 断线与恢复

1. 网络中断/本机休眠：窗口里的提示变为「连接断开，远端任务可能仍在运行」。
2. 自动重连（可配置）：恢复后刷新远端界面；断线期间远端任务不受影响（明确提示）。
3. 重连失败：显示错误分类与诊断入口，可手动重试。

### 5.4 多主机切换

- 侧边栏主机管理页点另一台的「打开」即切换（没有工具条，也不并行呈现）。
- 任何时刻只呈现一台远端；切换会关闭上一台的本地承载，远端任务继续运行。

### 5.5 远端服务未运行

连接管线自己负责远端 DSH 的启动：探测不到运行中的界面时，先把插件托管的 Node 准备到 `~/.dsh/remote-go/node`（缺失/过旧时自动安装或升级），再用 `npx` 固定本机版本把远端 DSH 拉起来，进度在本地展示，成功后直接接管整窗；失败按分类给原因与诊断入口（没有单独的「启动它」按钮）。

### 5.6 关闭与恢复

- 关闭视窗/退出本机 DSH：远端任务继续；下次打开回到该主机。

## 6. 远端侧内容要求（产品视角）

- 远端只需**原版 DSH**（能提供 Web 界面即可），**不需要安装本插件的任何远端组件**。
- 远端界面默认只在本机可访问（经 SSH 隧道），不对公网暴露。
- 远端访问令牌：优先由插件在远端启动界面时自动获取；获取不到时允许用户手工粘贴已有地址与令牌。
- 远端版本：能提供 Web 界面的 DSH 版本即可；版本差异只影响远端界面本身，本地不感知具体功能。
- 启动方式会影响「桌面功能」判定：由 SSH 会话启动时 DSH 会关闭宿主桌面功能；由 systemd / 计划任务启动时可能误开（对话框弹在远端屏幕上）。插件默认经 SSH 启动远端界面，并在诊断里检查该状态。
- 可选（P2）：本地发起「安装/升级远端 DSH」，只在远端执行，本地展示进度与结果。

## 7. 呈现模式与能力依据

### 7.0 DSH 的「整页切换」能力（已确认，2026-11-10）

查证 DSH 0.2.2-rc.1 客户端布局包 `@deepseek-ai/dsh-client-ui-layout`（本地解包副本 `_research/asar2/...`）：

- **全局面板**占据 root 作用域的 `main` keyed slot；`conversation` 是为会话界面保留的 key；`ctx.layout.selectPanel(id)` 选中已注册面板、传 `null` 回到会话界面；DSH 自带「插件」页就是默认组合里的一个全局面板。
- **`shell.overlay`** 是覆盖整个框架的根级插槽，可做真正的全屏层。
- 已安装的 `dshmarket` 插件同时注册了 `main` 全局面板与 `sidebar.panellist` 侧边栏入口，并用 `ctx.layout.selectPanel(id)` 切换——这就是「整页切换」的现成用法。

结论（历史记录，已被 §4.3 取代）：当时的结论是"整页切换可以做，有两种粒度"。最终实现只保留一种：桌面端 Chromium guest 接管**整窗**，本地侧边栏让位，底部注入主机条；没有 iframe 内嵌、没有 `shell.overlay` 沉浸模式。

### 7.1 模式对比

| 模式 | 本地要做什么 | 体验 | 主要限制 | 建议版本 |
|---|---|---|---|---|
| A 桌面 guest 接管整窗 | 侧边栏入口 + `dshDesktop.browser.acquire` + 连接 | 远端界面铺满窗口，底部注入主机条即切换器 | 只有桌面端有 guest 能力；浏览器里没有退路 | **V1 采用** |
| B 沉浸模式（全屏覆盖） | 在 A 基础上加 `shell.overlay` 全屏层 | 远端界面铺满窗口，干扰最少 | 需要浮动工具条/退出入口；遮挡本地提示 | V1.1 可选 |
| C 原生渲染（真 VS Code 式） | 会话映射、事件回灌、审批桥、版本适配 | 最原生 | 本地工作量最大，与 DSH 内部契约耦合 | V2 评估 |

> 结论：V1 用 A；V1.1 加 B；C 只在确实需要原生体验且愿意投入时再做。

## 8. 交互与状态规范

### 8.1 主机状态

| 状态 | 含义 | 视觉 | 可操作 |
|---|---|---|---|
| 未配置 | 刚添加，未连接过 | 灰点 | 连接、编辑、删除 |
| 连接中 | 正在建立 SSH/隧道/打开界面 | 蓝点 + 进度 | 取消 |
| 已连接 | 远端界面可用 | 绿点 | 打开、断开 |
| 断线 | 连接丢失，可恢复 | 黄点 | 重连、诊断 |
| 错误 | 连接/认证/指纹/服务失败 | 红点 | 重试、诊断、编辑 |
| 受限 | 能连但远端无法提供界面（版本/配置问题） | 紫点 | 诊断、查看原因 |

### 8.2 视窗状态

加载中（分步骤文案）→ 已就绪 → 断线（banner）→ 重连中 → 已就绪；加载失败只在窗口里显示一行普通提示，不出现空白视窗。

### 8.3 通知

- 连接成功/断开/重连：轻提示（toast）；断线时视窗内持续 banner。
- 主机状态变化：主机卡片即时更新。
- 可选远端提醒：本机通知 + 卡片标记（§4.6）。

### 8.4 错误文案（分类 + 下一步）

| 分类 | 标题示例 | 下一步 |
|---|---|---|
| 网络 | 「连不上这台服务器」 | 检查地址/端口/网络；跳板机先测跳板 |
| 认证 | 「SSH 认证没有通过」 | 检查用户名与密钥/Agent |
| 指纹 | 「主机指纹变了」 | 确认是否重装过服务器后再继续 |
| 远端服务 | 「远端 DSH 没有在运行」 | 由连接管线自动启动；检查托管 Node 的下载（nodejs.org/npmmirror）、npm registry，或查看诊断 |
| 远端界面 | 「远端界面打不开」 | 检查远端 DSH 版本与配置；复制诊断 |
| 版本 | 「npx 拉不到本机版本」 | 确认本机版本已发布到 npm registry |
| 运行时 | 「远端 Node 自动安装失败」 | 检查网络/磁盘/架构（musl 需 `apk add nodejs npm`）；或手动安装 Node 后重试 |

### 8.5 危险操作（都在远端界面里，本地只做提示）

- 本地只负责：首次进入时提示「你正在操作远端服务器」；关闭视窗时提示「远端任务会继续运行」。
- 升级、插件安装、凭据修改等由远端界面自身确认，本地不重复拦截（避免双份规则不一致）。

## 9. 安全设计（用户可见部分）

1. **SSH 认证**：私钥文件（默认 `~/.ssh/id_ed25519`，可浏览选择）或密码；密码默认仅本次使用，勾选后可存进 DSH 凭据存储（`hosts.json` 里永远没有密码）。首次连接确认主机指纹，指纹变化强提示。不支持 SSH Agent。
2. **本地零暴露 + 回环硬规则**：远端界面只绑回环 + SSH 隧道；本地不监听公网地址。远端 DSH 的 cookie 是 `SameSite=Strict` 且按 authority 绑定，**跨 site 地址（公网域名 / Tailscale IP）嵌不进来**，必须映射为 `127.0.0.1:<本地端口>`（ssh -L，或 frpc 的 stcp/xtcp visitor）。
3. **访问令牌**：默认只在内存中使用，不落盘、不写日志；用户可在设置中允许保存（明确提示风险）。
4. **多主机隔离**：每台主机使用独立的本地端口/存储分区，登录态不串号（产品层面表现为：切主机不会串到另一台的界面）。
5. **信任边界**：本地视窗里显示的是远端 DSH 的界面，所有操作在远端执行；提示用户不要在本机视窗里向不可信远端粘贴敏感信息。
6. **guest 限制**：桌面端 guest 会话禁用下载、拒绝权限请求、弹窗转交宿主。这些是壳写死的行为，界面不提供任何"打开新窗口"的逃生通道。

## 12. 与 v0.2「全控制台」方案的关系

| 维度 | v0.2 全控制台 | 本版薄客户端 |
|---|---|---|
| 本地工作 | 重做会话/审批/文件/终端/管理界面（7–9 周） | 只做连接/视窗/状态（1–2 周） |
| 能力覆盖 | 本地原生呈现，可深度集成 | 完全覆盖（= 远端 DSH 界面的全部能力） |
| 体验 | 更像本机应用 | 像"在本地整页里操作远端 DSH"（整窗接管/沉浸模式） |
| 版本耦合 | 高（跟随 DSH 内部契约） | 低（只依赖 SSH 与远端界面存在） |
| 本地 agent 编排 | 支持 | 不支持（若需要，V2 加工具/桥接） |
| 通知/审计 | 可做完整 | 只做可选通知，无本地审计 |

**结论**：先用薄客户端满足「完全控制服务器上的 DSH」（控制 = 使用远端 DSH 自己的完整界面）；如果后续确实需要本机 agent 直接编排远端、或要求原生会话体验，再在该基础上渐进增强（通知桥 → 本地 agent 工具 → 原生渲染），而不是一上来重做一遍 UI。

## 15. 同类项目调研结论（2026-11-10）

调研了 8 个 DSH 远程类项目（dsh-remote-dsh、dsh-remote-gui、dsh-remote-tunnel、dsh-remote-explorer、dsh-remote-local-plugin、dsh-zen-remote、dsh-ssh-desktop、dsh-multi-instance）与 3 个邻近产品。调研结论见本节；原始调研报告已不再随仓库保留（可从 git 历史取回）。

### 15.1 对需求的增补（进入 V1）

| 增补 | 理由 |
|---|---|
| SSH 别名自动发现（`~/.ssh/config`；`known_hosts` 只读且跳过哈希条目） | dsh-remote-tunnel 证明这是降低接入摩擦的关键；哈希条目无法反解，只报数不猜 |
| 远端宿主检查：桌面功能干扰项 + 启动方式建议 | systemd 启动的远端会被 DSH 当作「本机工作站」，目录对话框/Open In 弹在远端屏幕；dsh-remote-dsh 用 5 组配置修正 |
| 隧道「收养」与去重 | 本机重启后复用还在监听的隧道，避免重复 spawn；dsh-remote-gui / ssh-desktop 都做了 |
| 诊断导出默认脱敏、token 只在内存、主机注册表不含凭据 | dsh-ssh-desktop 的诊断脱敏、dsh-remote-gui 的 cookie 内存缓存是成熟做法 |
| 入口在空会话也可用（侧栏入口） | dsh-remote-tunnel 的命令卡/状态条在空会话不渲染，侧栏面板才是保底入口 |

### 15.2 必须避开的坑（Top 8）

| # | 坑 | 我们的动作 |
|---|---|---|
| P1 | **回环硬规则**：`SameSite=Strict` 硬编码，公网域名 / Tailscale IP 的 iframe 连 index 都 401 | 只接受 `127.0.0.1:<端口>`；非回环地址当场警告并给出替代方案 |
| P2 | **iframe cookie 种入/持久化未验证**（dsh-remote-gui 因此改为原生面板） | V0 闸门先验证；失败就用「在新窗口打开」正式降级 |
| P3 | **token 发现依赖 systemd unit 名**（`dsh-web`） | 插件自己接管远端 web 的启动并解析 stdout；兜底用户粘贴 URL+token |
| P4 | **嵌套实例**：把本机实例嵌进面板 → 套娃卡死 | 默认目标永远远端；本地模式不嵌 iframe |
| P5 | **远端桌面功能误开**：对话框/Open In 出现在远端屏幕 | 经 SSH 启动远端界面（带 SSH 环境信号）；诊断检查 5 组配置 |
| P6 | **契约漂移**：RPC args key 因方法而异（`session/list` 是 `_request`）、流式必须走 WS、HTTP 200 也可能是失败 | 只依赖少量端点；集中适配；看 `result.ok`；能力探测 |
| P7 | **会话噪声与归档非权威**：346 条里 317 条子代理；归档只是本机视图 | 交给远端 GUI 自己处理；不在本地伪造状态 |
| P8 | **token/文档风险**：profile 里存 token 的警告；README 与代码漂移 | token 默认不落盘；文档只写「已验证」的事实，发布前实测 |

### 15.3 结论

- 方向成立：dsh-remote-dsh 证明「回环 + 整页嵌入远端 GUI」可行；dsh-remote-gui 证明「本地只管隧道/凭据、界面交给远端或重写」两条路都存在。
- **最接近的现成实现是 `graydovee/dsh-remote-window`（alpha.6）**：已用**同源 portal 反代**解决 iframe cookie，主区全屏显示远端官方 UI，支持本机模型自动代理 / server 模型、host key pin、per-client profile 与 runtime；代价是远端更重（常驻 profile + 专属插件 + 独立 runtime）。
- 因此自研只剩两条路：**轻量差异化**（零远端专属组件、只用远端已有 dsh web + SSH，自己做 portal 或接受外部窗口降级）或 **fork/采用**该实现。
- 最大风险仍是 **iframe 的 cookie 种入/持久化**：必须 V0 先验；已有 portal 正解可参考。

## 16. 远端运行时与运维管理（v0.6 增补）

> 吸收同类项目设计 + 用户新增需求：远端只要 Linux + 能访问官方 Node 源与 npm registry，插件就自动装好自己的 Node 并拉起 DSH、远端版本与本机一致、本机关闭后远端可继续存活（可配置）、远端插件与设置可在本机管理。

### 16.1 新增内容清单

| 编号 | 内容 | 说明 | 优先级 |
|---|---|---|---|
| L13 | 远端运行时 | 插件托管 Node（版本 = 本机 DSH `engines.node` 下限，固定安装到 `~/.dsh/remote-go/node`，官方 tarball + SHA-256 校验，不碰系统 Node）+ `npx` 精确版本拉起 DSH | P0 |
| L14 | 版本一致性 | 目标版本 = 本机 DSH 版本；npx 预检不一致直接失败，不静默混用 | P0 |
| L15 | 远端存活策略 | 关闭本机后远端可继续运行（默认）/ 退出即停 / 空闲 N 分钟后停，按主机可配 | P0 |
| L17 | 远端设置管理 | 在本机读取/编辑远端常用设置，保存前 diff、备份、校验，按需重启远端服务 | P1 |

### 16.2 远端运行时：插件托管 Node + npx 固定版本

| 远端现状 | 做法 | 用户看到 |
|---|---|---|
| 能访问 nodejs.org / npmmirror（有没有系统 Node 都一样） | 先把**固定版本**的官方 Node Linux 构建（版本 = 本机 DSH `engines.node` 下限，`.tar.gz`，SHA-256 校验）解压到 `~/.dsh/remote-go/node/v<version>`，再用它的 `npx` 执行 `env DSH_HOME=~/.dsh … npx -y @deepseek-ai/dsh@<本机版本> --profile <profile> --no-open --port 0` | 首次约 3–5 分钟（托管 Node 下载 + DSH 冷缓存下载，随网络而定），之后复用；下载/解压/启动都有进度 |
| 已装托管 Node 不是目标版本 | 安装目标版本，成功后清理旧版本目录 | 自动完成，不打扰 |
| 网络不可达 / 磁盘不足 / 架构不支持 / musl / glibc < 2.28 / 缺 curl+wget | 明确失败 + 可复制的准备步骤；**不会**改用系统 Node | 错误原因与下一步，不假装成功 |

**原则**：`npx` 仍是唯一的启动路径，Node 只由插件提供且**固定版本**（跟着本机 DSH 的 `engines.node` 走，不追最新补丁）：永远不修改系统 Node、不需要 root、不做隔离 DSH home；失败时停在**可解释、可重试**的状态，**没有系统 Node 兜底**。

### 16.3 版本一致性

- 目标版本**恒取本机 DSH 版本**（例如 `0.2.2-rc.1`），而不是 npm 的 `latest`；没有设置项，也没有「沿用远端」选项。
- 连接前用 `npx -y @deepseek-ai/dsh@<本机版本> --version` 预检：冷缓存下载在这里发生，回读版本必须与本机一致，否则 `version-mismatch` 直接失败（不静默混用）。
- 远端 web 一律由这条固定版本命令拉起；`~/.dsh` 里如果有别的版本在跑，不会被收养（run 注册表还要匹配 `dshHome` 与 `profile`）；若注册表指向的是本插件自己留下的旧版本实例，会先停止它再拉起匹配版本。
- 非本插件启动的 DSH 进程（手工 `dsh web` 或另一个客户端启动）会触发 `conflict-pending`，列出进程并让用户选择：停止它并启动受管实例 / 保留它另起一个（共享 `~/.dsh`，给出警告）/ 取消连接；120s 未选择按取消处理。
- 主机卡片/诊断仍展示 `versionParity`（本机 vs 远端）作为事实陈述；在托管 Node + npx 模型下两者恒等，除非远端被外部进程改动。
- 远端 profile 里若有 bundle（如 `@goldenpigeon/dsh-remote-agent`）为原生 UI 关闭 `api-remotes`（浏览器 Remote-Event 载体），启动前会用 `--patch <state>/browser-carrier.patch.yml` 只对**本次启动**重新启用该行，不改用户的 profile；否则浏览器客户端会停在「failed to load plugins / $events unavailable」。
- run 注册表带 `launch` 标记：不带该标记（旧启动方式）或不可收养的实例会先停止再按当前方式拉起，避免收养一个页面起不来的旧进程。
- 本机升级后，远端下次连接自动跟随新版本（npx 缓存里会保留旧版本，但不再被使用）；托管 Node 的目标版本随本机 DSH `engines.node` 的下限走（如 `>=24.9.0` → 24.9.0），版本变化时远端会自动安装新版本并清理旧目录。

### 16.4 本地关闭后的远端存活（可配置）

| 策略 | 行为 | 适用 |
|---|---|---|
| 保持运行（默认） | 关闭本地窗口/退出后，远端 DSH 与任务继续；下次连接直接复用 | 长任务、服务器常驻 |
| 退出即停止 | 正常退出时停止远端服务并清理隧道 | 临时使用、按量计费 |
| 空闲停止 | 本机断开后空闲 N 分钟自动停止（可配 1–1440 分钟，默认 15） | 平衡成本与体验 |

- 按主机配置，首次关闭时提示当前策略并允许切换。
- 异常退出（崩溃/断电）：远端不应被立刻杀；由租约/心跳判断，超过阈值后才按策略清理（不做「客户端一断就杀」）。
- 服务托管：用 `setsid` + `nohup` 在用户目录里拉起远端 `dsh web`，运行态写入 `run/web.json`（pid/port/version/profile/dshHome）；不依赖 systemd。停止/升级要显示影响（运行中的 turn 会取消）。
- 关闭本地时若有运行中任务，提示「远端会继续运行，下次打开可接续」或「将停止远端并中断任务」。

### 16.5 远端插件管理：不单独实现（使用远端插件市场）

- 决策：**本地不做插件管理面板**。插件安装/启用/禁用/卸载/更新全部在**远端 DSH 自己的插件市场/插件页**里完成——它就在我们嵌入的远端界面内，零额外本地实现，且与远端版本语义天然一致。
- 本地只提供两个便利：① 在「DSH 管理」里放一个「打开远端插件市场」的入口（切换到远端界面并定位到插件页）；② 版本不一致时提示先同步版本。
- 这样也避免重复维护一套「安装源/兼容性/失败回滚」逻辑；插件市场的行为由远端 DSH 自己负责。
- 参考：`dsh-remote-explorer` 同样选择「远端插件由远端自管」；我们的区别只是把入口做进本地控制台。

### 16.6 远端设置管理（本机操作）

- 入口：主机详情 →「DSH 管理」→ 设置。
- 常用项可视化（默认模型、权限预设、上下文/压缩、通知、插件配置等）；高级项只读 + 受控编辑。
- 保存流程：**读取 → 编辑 → diff 预览 → 校验 → 备份 → 写入 → 按需重启**；失败自动回滚备份。
- 明确标注「仅影响远端」；与远端界面同时修改时以远端为准并在保存前检测冲突。
- 版本不一致或远端不支持该设置项时隐藏/置灰，并说明原因。

### 16.7 页面与流程改动

- **主机详情**新增 Tab：「概览 / 服务 / DSH 管理（版本/设置/凭据/日志；插件跳转到远端插件市场）/ 连接」。
- **接入向导第 3 步**展示远端能力清单（Linux / 架构 / glibc 或 musl / curl 或 wget / 磁盘）与托管 Node 的安装结果、目标版本（= 本机版本）；没有「自举方式」可选，也不提供离线或隔离安装入口。
- **关闭流程**：关闭视窗/退出时按主机策略提示（保持运行/停止/空闲停止），不静默改变行为。
- **管理流程**：设置保存有「diff/影响 → 确认 → 执行 → 结果」四步并进审计；插件操作在远端插件市场内完成，本地只记录「已打开」。

### 16.8 安全与权限（增补）

- 远端运行时命令只使用**固定模板**（托管 Node 的 `npx … --version` 预检、`npx … --profile <profile> --no-open --port 0` 启动），不接受用户拼接的任意 shell。
- 托管 Node 只从插件内置的官方源（nodejs.org，失败回退 npmmirror）下载，URL 由常量、DSH 的 `engines.node` 与远端架构拼出；解压前必须通过官方 `SHASUMS256.txt` 的 SHA-256 校验；永远不修改系统 Node。
- npx 使用精确版本号；不做隔离 DSH home；失败不静默降级（**没有系统 Node 兜底**）。
- 设置写入、服务重启都是高权限操作：二次确认 + 影响说明 + 审计；插件安装由远端插件市场自己确认，本地不重复拦截；多用户共享主机时明确「操作的是该 SSH 账号的环境」。
- 设置写入前备份（0600），保留最近 N 份；写入失败回滚。
- 远端服务默认只绑 `127.0.0.1`，经 SSH 隧道访问；token 仅在内存/0600 文件。

## 附录 · 5 分钟演示脚本

1. 本机 DSH → 侧边栏「远程主机」→ 空态 →「添加第一台服务器」。
2. 填 SSH 别名 → 指纹确认 → 探测到远端 DSH 已安装 →「打开」。
3. 整窗切换为远端 DSH 界面；本地侧边栏让位，底部注入的主机条负责换主机与离开。
4. 在远端界面里新建会话、发消息、处理审批、打开文件与终端（全部是远端能力）。
5. 断网 30 秒：窗口提示「远端任务可能仍在运行」；恢复后自动重连。
6. 切回主机清单，添加第二台，切换验证互不影响。

## 附录 · v0.7 产品调整（2026-11-11，已实现）

产品负责人对 v0.6 的本地形态做了三处调整，实现以本节为准：

1. **不再使用「远程入口」这个名字，也不再占用侧边栏入口。** 插件市场显示名为 dsh remote go；本地界面统一称「远程主机」（Remote hosts）。
2. **主机配置移入设置目录**：本地 DSH 的 Settings 增加「远程主机」页（settings.section），主机清单、添加/编辑/删除、连接/断开、诊断、插件设置、打开远程界面都在这里完成。
3. **工作区按远端区分，同时保留本地工作区**：远程面板左侧新增「工作区」栏，包含「本地工作区」分组和每台远端主机的工作区分组（数据分别来自本机与远端 DSH 的 storages/workspace.json）；点击本地工作区回到本地会话，点击远端工作区打开该主机的远程面板。
   - 限制说明：DSH 内置侧边栏的「工作区」列表是 sidebar.workspaces 单占槽位（由 dsh-client-ui-workspace 独占），第三方插件无法向其追加分组；因此该区分落在插件自己的面板内，本地侧边栏列表保持原样、互不影响。若后续 DSH 开放工作区分组扩展点，可再迁移到内置侧边栏。
     - **后续进展（v1.1）**：宿主提供了可选的 `workspaceRegistry` 服务，插件可以注册工作区。现已接入：连接主机时额外在本地侧边栏注册 `Remote: <主机名>` 承载镜像会话；面板内工作区栏随后整体移除，侧边栏工作区是唯一位置。详见 `docs/session-design.md` §4.3。

以上调整不改变 v0.6 的核心架构（薄客户端 / 回环隧道 / npx 运行时 / 版本一致 / 存活策略）；呈现方式已由回环 iframe 改为桌面端 guest 接管整窗（见 §4.3）。
